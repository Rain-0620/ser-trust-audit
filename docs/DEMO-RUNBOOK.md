# 演示运行手册 — 提示词、操作步骤、录屏

适用：AGH 会话录制（空跑验证 + 正式录制）。前置条件：AGH 服务已在 4180 端口运行。

---

## 0. 一次运行会发生什么（先有预期）

| 阶段 | Agent 的动作 | 耗时 |
|---|---|---|
| 读能力 | `catalog` —— 看到 9 个扰动族、指标说明、**和它自己推荐的 5 步工作流** | 秒级 |
| 建基线 | `probe` | ~2 分钟 |
| 探索 | 第一轮 `sweep`（自己挑几个**不同机制**的扰动） | ~1 分钟 |
| 反馈 | 读结果 → 决定第二轮：把机制推到极限 | ~1 分钟 |
| 定位 | 对异常条件跑 `curve`，括号出阈值 | ~2 分钟 |
| **全量确认** | `battery` —— **反复调用约 10 次**直到 `status=complete` | **~80 分钟** |
| 成文 | 写信任边界报告 | ~1 分钟 |

**总时长约 90–100 分钟。** 关键点：`battery` 一次装不下（AGH 单次 shell 超时 10 分钟，
全量要 80 分钟），所以它设计成**可续跑**——每次调用跑 8 分钟并报"还剩 N 个条件"。
Agent 需要自己反复调用。**这段"反复调用直到完成"本身就是一次真实的反馈处理行为，是加分的。**

## 1. 运行前准备（每次运行都要做）

### 1.1 清空 battery 状态（**必做，否则记录会变成"跳过"**）

```powershell
cd D:\ser-audit
.venv\Scripts\python.exe audit.py battery --status
```

如果显示 `complete` 或 `in_progress`，必须重置，否则 Agent 调 `battery` 时会直接复用完
已有的结果，AGH 记录里只会留下"已完成/跳过"，**那就不是"真正测出来"的证据了**：

```powershell
.venv\Scripts\python.exe audit.py battery --reset
```

> 重置后第一次调用会重新测量干净基线（约 85 秒），之后各次调用复用缓存。

### 1.2 让服务可用

```powershell
# 检查服务
Test-NetConnection 127.0.0.1 -Port 4180 -InformationLevel Quiet
# 若未运行：
& "D:\agh\start-agh.ps1" -Workspace "D:\ser-audit"
```

浏览器打开 **http://127.0.0.1:4180/**

### 1.3 干净的执行环境

- 打开**专注助手 / 免打扰**（Win 键 → 设置 → 系统 → 专注），避免弹窗录进去
- 关掉无关的浏览器标签、聊天软件、邮件客户端
- 浏览器 **Ctrl+= 放大到 110%–125%**，让录屏里字看得清
- 隐藏书签栏（Ctrl+Shift+B）
- **不要出现任何个人账号、邮箱、聊天记录**

## 2. 提示词（直接整段复制粘贴）

> 下面这段是**唯一的提示词**，空跑和正式录制用同一段。
> 注意它**没有**提到 `battery`——Agent 需要自己从 `catalog` 里发现它。
> 这是刻意的：命令是它自己选的，才算"任务规划"。

```
使用 ser-trust-audit 技能，审计工作区里的语音情感识别模型。

调用方式（在工作区根目录下执行）：
  .venv\Scripts\python.exe audit.py <子命令> [参数]

先跑 catalog，看清楚这个工具提供哪些能力、以及它自己建议的工作流程是什么。然后自己规划实验。

要求：

1. 先建立干净基线：准确率是多少、相对随机水平如何、模型指纹是什么。

2. 自己规划第一轮扰动实验。要挑能区分不同失效机制的（例如加性噪声、带宽损失、编解码失真、
   韵律变化各选一个），不要挑同一机制的多个变体。

3. 解读每个条件的完整指标，不要只看准确率：
   - balanced_accuracy 要和 chance_level 比，不要和 1.0 比
   - mean_normalised_entropy 反映模型是否还在"思考"
   - majority_share 和 degenerate 说明模型是否已经塌缩成只会答一个类
   必须区分清楚「模型不确定」和「模型不再回答问题」——这是两种不同的失效，含义完全不同。

4. 对任何看起来异常的条件，不要只报那个数字，要去定位它：在那个族上用 curve 加密采样，
   把阈值找出来，并说明你的采样间隔是多少。

5. 检查你自己的测量是否有效。如果某个扰动得到的结果与干净基线完全一致，先怀疑这个变换根本
   没生效，而不是直接下「模型很鲁棒」的结论。

6. 探索阶段的实验用的是小样本，它用来找方向，不是可报告的结论。做完探索之后，按工具的指引
   做全量确认，并且**把确认阶段的结果作为报告依据**。

7. 报告里每个数字都必须来自工具输出。你自己推断出来的阈值要标注为推断，不要写成观测。

8. 最后输出一份信任边界报告，包含：
   - 审计范围：模型指纹、数据集划分、样本量与类别分布、随机种子、设备
   - 基线：干净准确率（带置信区间）与随机水平的对比
   - 逐条条件的发现：明确指出哪些扰动模型能耐受、哪些让它"犹豫"、哪些让它"塌缩"；
     对塌缩的条件给出定位到的阈值和定位方式
   - 信任边界：在哪些**可测量**的条件下不应采信该模型的输出
   - 局限：样本量、覆盖面、未测的扰动，以及哪些是推断而非观测

不要为了让结果好看而修改 audit.py 或模型。不要报告任何你没从工具拿到的数字。
```

## 3. 操作步骤

| # | 你要做的 | 说明 |
|---|---|---|
| 1 | 打开 http://127.0.0.1:4180/ | 确认界面加载正常 |
| 2 | 把上面**第 2 节整段提示词**粘进输入框，发送 | 这是"任务规划"的起点 |
| 3 | **第一次弹审批时，选「允许本会话」（allowed-session）** | **关键**：这一下覆盖后续**全部** shell 命令。不选的话你要点 30+ 次 |
| 4 | 之后就让 Agent 自己跑 | 它会 `catalog → probe → sweep → sweep → curve → battery...` |
| 5 | 看到它反复调用 `battery` | **这是正常的**，每次约 8 分钟，共约 10 次。不要打断 |
| 6 | 等它写出报告 | 最后一次 `battery` 返回 `status: "complete"` 后它会汇总 |
| 7 | 让会话结束，**不要关掉浏览器标签** | 需要它来导出记录 |

### 应急处理

| 情况 | 怎么办 |
|---|---|
| 某次 `battery` 调用超时/失败 | **进度已存盘**。直接给它发一句：`继续跑 battery，直到 status 为 complete` |
| Agent 卡住不动 | 发：`继续`。进度不会丢 |
| Agent 提前收工说"完成了" | 查 `audit.py battery --status`。若未 complete，发：`battery 还没跑完，继续调用它直到 status 显示 complete` |
| 中途电脑出问题 | 重启后跑 `start-agh.ps1`，恢复会话或重跑（battery 状态还在，可断点续传） |

## 4. 录屏

### 4.1 工具选择

**推荐 OBS Studio**（免费、稳定、可长时间录制）：
- 场景添加「窗口采集」→ 选浏览器窗口
- 输出：MP4，1920×1080，30fps
- 音频：想配解说就加麦克风；不配也行，后期打字幕

**没有 OBS 就用 Windows 自带 Xbox Game Bar**：
- `Win + G` 打开 → 点「捕获」小组件 → 开始录制
- 录的是当前前台窗口，输出到 `视频\捕获`
- 缺点：长时间录制偶尔掉帧，控制项少

**不建议**：手机拍屏幕（字看不清）、PowerPoint 录屏（长时间不稳）。

### 4.2 录制节奏

**全程录一次，后期剪成 3–5 分钟**（不要把 90 分钟压缩成"演一遍"）。

必须**不加速**保留的三段（这是评委看"闭环"的地方）：

1. **粘贴任务 → Agent 读 catalog → 给出第一轮计划**
   证明：测什么是它自己定的，不是提示词写死的
2. **审批弹窗 → 点「允许本会话」→ 命令开始执行**
   证明：人在回路，每一步都可审计
3. **Trace 视图逐步展开**
   证明：有完整的执行记录

**可以跳剪加速**的部分：

- `battery` 那 80 分钟 → 跳剪成 10–15 秒，配字幕：
  *"全量确认：53 个条件 × 1241 条话语，因单次调用有超时限制，Agent 分 10 次调用完成"*
- 每个 `battery` 调用之间的等待 → 直接切掉

### 4.3 建议成片结构（4 分钟版）

| 时间 | 内容 |
|---|---|
| 0:00–0:25 | 一句话说清：审计一个开源 SER 模型，找出它在什么条件下不可信 |
| 0:25–1:20 | **镜头 1**：粘贴任务 → Agent 自己规划（不加速） |
| 1:20–1:50 | **镜头 2**：审批 → 允许本会话（不加速） |
| 1:50–2:30 | **镜头 3**：Trace 视图展开 + battery 反复调用（跳剪 + 字幕） |
| 2:30–3:30 | 结果：两种塌缩签名 / 阈值 / **阈值依赖评测集**这个发现 |
| 3:30–4:00 | 信任边界结论 + 一句话收尾 |

### 4.4 录制检查清单

- [ ] 专注助手已开，无弹窗
- [ ] 浏览器已放大，字看得清
- [ ] 无个人账号/邮箱/聊天记录入镜
- [ ] 音频电平正常（若配解说）
- [ ] **先录 5 秒测试**，回放确认画面和声音都对，再正式开始

## 5. 跑完之后

### 5.1 立刻导出会话记录（运行证据，不可丢）

```powershell
cd D:\ser-audit
$entry = "D:\agh\agnes-harness\packages\cli\dist\local\agnes.mjs"
node $entry sessions list --profile local-dev
# 记下最新的会话 id，然后：
node $entry export <会话id> --html -o "D:\ser-audit\evidence\session\v2-agent-run.html" --profile local-dev
node $entry export <会话id> --format agnes -o "D:\ser-audit\evidence\session\v2-agent-run.agnes.json" --profile local-dev
```

### 5.2 我来做的核对

把会话 id 告诉我，我会核对三件事：

1. AGH 记录里 `battery` 的调用次数与最终 `status`
2. 记录里的数字与 `outputs/battery/` 里产出的数字是否一致
3. Agent 是否只引用了确认阶段的数字（而不是拿探索性的小样本数字当结论）

### 5.3 之后

确认通过后：把 `outputs/battery/` 的结果作为最终数字重新生成报告，
再录一次（或直接用这次的录像），然后进入提交材料撰写。

## 6. 空跑 vs 正式录制的区别

| | 空跑（验证） | 正式录制 |
|---|---|---|
| 是否录屏 | 不录 | 录 |
| 提示词 | 同上 | 同上 |
| 是否 `--reset` | **要**（让 Agent 真的跑 battery） | **要** |
| 目的 | 确认 Agent 能读通 v2 协议、会反复调 battery | 产出运行证据 + 视频素材 |
| 时长 | 90–100 分钟 | 90–100 分钟 |

**如果空跑那次的记录已经完全覆盖了报告的数字，其实它本身就是合格证据**——
那种情况下正式录制可以只录"探索阶段"那几分钟，battery 部分用空跑时的画面拼接。
要不要这么做，等空跑结果出来再定。
