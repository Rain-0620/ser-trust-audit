# 让 Agent 去审计一个语音情感识别模型：它什么时候开始胡说八道？

> 我们不给模型测"准确率"，我们给它测"信任边界"。
> 结论先说：这个模型在干净语音上平衡准确率 **0.776**，但它有 **两种完全不同的失效方式**，
> 而且**阈值不是模型的固有属性**——同一个模型、同一个条件，换个评测集就可能得出相反结论。
> 整个过程中，执行审计的 Agent 还发现了我们写审计工具时留下的 **两个真 bug**。

---

## 1. 问题：准确率不告诉你什么时候不能用

语音情感识别（SER）模型现在很容易拿到：HuggingFace 上随便一个微调好的 wav2vec2，在 IEMOCAP 这类标准测试集上跑个 70%~80% 的四分类准确率并不难。

但真正要把它放进产品里，你需要回答的不是"它准不准"，而是：

- 用户用手机在**嘈杂街头**录的语音，它还能用吗？
- 音频被**压缩成低码率**传输过，它还靠谱吗？
- 麦克风**音量差很多**，会不会影响结果？

更关键的是：**它的失效长什么样？**

这里有一个常被忽视的区别：

| 失效方式 | 表现 | 后果 |
|---|---|---|
| **不确定** | 准确率下降，但概率分布仍然分散 | 可以靠置信度过滤掉 |
| **塌缩** | 输出几乎恒为一个类，准确率掉到随机水平附近 | **监控看不出来**，因为它还在"正常输出" |

第二种最危险。一个模型如果对所有输入都回答"中性"，准确率可能是 30% 左右——看起来像"效果不好"，实际上是**它已经不再回答问题了**。如果你的质量监控只看准确率能不能过某个阈值，你抓不到这种失效。

所以我们做的工具，核心不是测准确率，而是**检测塌缩并定位它的边界**。

---

## 2. 方法

### 2.1 三层结构

```
判断层    Agnes 3.0 Flash（大模型）—— 规划实验、解读结果、发现异常、决定下一步
治理层    Agnes Harness —— 会话留痕、命令审批、工具调度
能力层    audit.py + SKILL.md —— 9 族扰动、11 项指标、统计检验（自研）
```

为什么这么分？因为**确定性的事不该交给模型做**。扰动怎么施加、置信区间怎么算、配对检验怎么做——这些必须是可复现的代码。模型只负责"该测什么、结果说明什么、下一步做什么"这类判断。

### 2.2 九族扰动

每一族都把一个人为可理解的参数映射到一个确定性的音频变换，并且**把随机性全部钉死**（这一点后面会讲，我们在这里栽过跟头）：

| 族 | 单位 | 模拟的现实问题 |
|---|---|---|
| `gaussian_snr` | dB | 加性环境噪声 |
| `white_noise` | 幅度 | 固定幅度噪声 |
| `lowpass` / `highpass` | Hz | 带宽受限（电话、远场麦克风） |
| `mp3` | kbps | 编解码丢失 |
| `clipping` | 削波百分比 | 录音过载 |
| `gain` | dB | 音量/录音电平差异 |
| `pitch` | 半音 | 说话人/韵律不匹配 |
| `timestretch` | 倍率 | 语速不匹配 |

### 2.3 塌缩怎么判定

我们用一个显式的约定：

> `majority_share >= 0.75`（一个类占了 3/4 以上输出）
> **或** `mean_normalised_entropy <= 0.30`（概率分布几乎不分散）

但**约定只是约定**。所以每个条件我们还会给出 `P(degenerate)`——**bootstrap 重采样中判定为塌缩的比例**。一个 P(deg) = 0.55 的判定是掷硬币，不能当结论用。

### 2.4 每一条结论都带不确定性

- **主指标是平衡准确率**（macro 平均召回），不是裸准确率——因为全量数据的类别分布不均，裸准确率会奖励"多猜常见类"
- 每个条件都给 **95% bootstrap 置信区间**（2000 次重采样）
- 每个条件与**同一批话语**的干净基线做**配对 McNemar 精确检验**
- 同族内部做 **Holm-Bonferroni 多重比较校正**

### 2.5 两阶段：先探路，再确认

这是最容易被忽略、但最重要的一条。

探索阶段用小样本（每类 24 条，共 96 条），快，用来找方向。**但它不是证据**——小样本的置信区间宽、塌缩判据噪声大。

确认阶段在**整个 session 的全部 1241 条四类话语**上重测 53 个条件。**报告只引用确认阶段的数字。**

我们踩过这个坑：探索阶段把 `lowpass:1000 Hz` 判成了"边缘塌缩"（P(deg) = 0.263），确认阶段在 1241 条上重测是 **P(deg) = 0.00，完全健康**。如果不做确认阶段，这就是一条假发现。

## 3. 发现

**测试对象**：`superb/wav2vec2-base-superb-er`（微调版 wav2vec2-base，四分类）
**数据**：IEMOCAP Session5 全部 1241 条四类话语（类别不均：happy 442 / neutral 384 / sad 245 / angry 170）
**设备**：单张 GTX 1650

### 3.1 基线

| 指标 | 值 |
|---|---|
| 平衡准确率 | **0.7761**，95% CI [0.7522, 0.8009] |
| 准确率 | 0.7736 |
| 每类召回 | angry 0.747 / happy 0.760 / sad 0.837 / neutral 0.760 |
| 随机水平 | 0.25 |

干净状态下这个模型是**好的**——四类召回相当均衡，没有明显的类别偏置。53 个条件里 10 个判为塌缩。

### 3.2 两种塌缩签名（最有意思的一条）

这不是"退化"，而是**塌缩到两个不同的常数类**，取决于破坏的是信号的哪一部分：

| 塌缩到 | 触发机制 | 实例 |
|---|---|---|
| 常数 **happy** | **加性噪声** | `gaussian_snr:2dB`（占比 0.81）、`white_noise:0.02`（0.80）、`gaussian_snr:0dB`（0.87） |
| 常数 **neutral** | **带宽/编解码/时域** | `mp3:8kbps`（0.84）、`timestretch:1.5×`（0.81）、`lowpass:700Hz`（0.73） |

而且**触发的判据也不同**：

- 噪声族走的是 **majority_share ≥ 0.75** —— 一个类"吃掉"了输出
- `lowpass` 族走的是 **entropy ≤ 0.30** —— **它还在输出四个类，但"自信地答错"**

看 `lowpass` 那三个点：

| 条件 | 平衡准确率 | 最大类占比 | 熵 | 判定依据 |
|---|---|---|---|---|
| `lowpass:850Hz` | 0.503 | 0.62 | 0.29 | **熵规则** |
| `lowpass:800Hz` | 0.492 | 0.65 | 0.28 | **熵规则** |
| `lowpass:700Hz` | 0.437 | 0.73 | 0.24 | **熵规则** |

准确率 0.44~0.50——比随机水平（0.25）高一倍，看起来"只是效果差了点"。但熵已经掉到 0.30 以下，**它其实已经不再真的在判断了**。

> **这一条对工程实践的意义**：如果你的监控只看准确率阈值（比如"低于 0.5 就报警"），噪声型的塌缩（准确率 0.25 左右）能抓到，但**带宽型的塌缩（准确率 0.44~0.50）会漏掉**。你需要监控的是**预测多样性**，不是准确率。

### 3.3 一个反直觉的结果：破坏性失真能扛，音量扛不住

| 条件 | 平衡准确率 | 变化 |
|---|---|---|
| `mp3:32 kbps` | 0.7623 | −0.014 |
| `mp3:64 kbps` | 0.7647 | −0.011 |
| `clipping:10%` | 0.7370 | −0.039 |
| `clipping:30%` | 0.5845 | −0.192（未塌缩） |
| **`gain:+20 dB`** | **0.6888** | **−0.087** |
| **`gain:−20 dB`** | **0.6006** | **−0.175** |
| **`gain:−30 dB`** | **0.5246** | **−0.252** |

**削波 30%、MP3 压到 32kbps，它基本没事。但仅仅把音量整体放大或缩小 20 dB，就损失了 0.09~0.18。**

这是一个"换个麦克风就会发生"的变化。**"鲁棒性"不能对"无害变换"想当然**——你必须实测。

### 3.4 定位到的阈值

每一族的阈值都是**在相邻采样点之间括号出来的推断**，不是观测值：

| 族 | 最后一个健康点 | 第一个塌缩点 | 括号区间 |
|---|---|---|---|
| `gaussian_snr` | 5 dB（P(deg)=0.00） | 2 dB（P(deg)=1.00） | **[5, 2] dB** |
| `lowpass` | 900 Hz（P(deg)=0.13） | 850 Hz（P(deg)=0.83） | **[900, 850] Hz** |
| `mp3` | 16 kbps（P(deg)=0.06） | 8 kbps（P(deg)=1.00） | **[16, 8] kbps** |
| `white_noise` | 0.005（P(deg)=0.00） | 0.02（P(deg)=1.00） | **[0.005, 0.02]** |
| `timestretch` | 1.3×（P(deg)=0.00） | 1.5×（P(deg)=1.00） | **[1.3, 1.5]** |
| `highpass`（至 800 Hz） | — | 范围内**无塌缩** | — |
| `clipping`（至 30%） | — | 范围内**无塌缩** | — |

采样步长：`gaussian_snr` 在 6–10 dB 区间用 0.5 dB，`lowpass` 在 700–1100 Hz 区间用 50 Hz。

### 3.5 阈值不是模型的固有属性（最重要的方法学结论）

我们做了三种独立验证，结论一致指向同一件事：**"塌缩阈值"这个说法本身是有条件的。**

**（1）同一 session、同一条件、换评测集构成 —— 判定会翻转**

| 条件 | 全量 n=1241 | 平衡子集 n=192 |
|---|---|---|
| `lowpass:900 Hz` | **未塌缩**（P(deg)=0.01） | **塌缩**（P(deg)=0.58） |

全量数据说"健康"，平衡子集说"塌缩"。而平衡子集那个判定本身 P(deg)=0.58——**是掷硬币**。诚实的说法是"边界区域"，不是"阈值"。

**（2）换 session —— 深度退化稳定，临界条件不稳定**

在 5 个 session 上各测一遍（每类 48 条，共 192 条）：

| 条件 | 塌缩的 session 数 | 判定 |
|---|---|---|
| `gaussian_snr:7.5 dB` | 0 / 5 | **稳定** |
| `gaussian_snr:4 dB` | 2 / 5 | 不稳定 |
| `lowpass:900 Hz` | 2 / 5 | **不稳定** |
| `lowpass:600 Hz` | **5 / 5** | **稳定** |

**深度退化的条件（`lowpass:600`）在任何 session 上都塌缩；临界条件（`lowpass:900`）只在 2/5 的 session 上塌缩。** 这就是"真发现"和"阈值假象"的区别。

**（3）换抽样种子 —— 只变抽样，其余全不变**

同一 session、同一条件、同样的每类 48 条，换 5 个独立抽样：

| 条件 | 塌缩的抽样数 |
|---|---|
| `gaussian_snr:7.5` | 0 / 5 |
| `gaussian_snr:4` | 0 / 5 |
| `lowpass:900` | **2 / 5** |
| `lowpass:600` | **5 / 5** |

`lowpass:900` 的"不稳定"**经受住了这一层检验**——没有 session 差异、没有条件差异，纯粹是抽样噪声就能让判定在 5 次里翻转 2 次。

**（4）附带发现：基线本身也不是常数**

| Session | 平衡准确率 | 95% CI |
|---|---|---|
| Session1 | 0.635 | [0.568, 0.699] |
| Session2 | 0.792 | [0.739, 0.848] |
| Session3 | 0.818 | [0.763, 0.870] |
| Session4 | 0.844 | [0.795, 0.891] |
| Session5 | 0.807 | [0.752, 0.860] |

**跨度 0.209**，Session1 的置信区间和 Session3/4 完全不重叠。所以**引用这个模型的任何准确率都必须注明是哪一 session**——单个数字不是模型的属性。

## 4. 工程：审计工具自己的四个缺陷

这部分可能是最值得分享的，因为它说明了一件事：**写一个"审计工具"比写一个"测量脚本"难的地方在哪。**

四个缺陷里，**两个是执行审计的 Agent 发现的，两个是我们自己在验证一致性时发现的。**

### BUG-1：变换根本没生效，而失败被静默伪装成"结果"

Agent 报告：`clipping` 族的所有指标与干净基线**逐位相同**（0.6979 / 0.369 / 0.2917，连每一类召回都一样）。

追下去发现两层问题：

1. **类型错误**：`ClippingDistortion` 要求 `int`，我们的参数解析把它们全转成了 `float` → `TypeError`，96 次调用全部失败
2. **更严重**：异常分支写的是 `sample = wave`——**失败就退回原始音频**。于是"96 次全部失败"被伪装成"和干净音频一模一样"，在结果表里长成一行"模型对削波鲁棒"

**这是审计工具最该防的失效模式。** 修复后：失败不再回退，条件标记为 `valid: false`（UNMEASURED），并新增 `clips_actually_modified` 字段记录变换实际改动了多少条音频。

值得一提的是：**Agent 拒绝了那个数字**。它把这个族标为"未测量"，明确不写鲁棒性结论，并且**没有擅自去改工具**——它说工具是"记录仪器"，审计中途改仪器是错的。

### BUG-2：目录里的方向标反了

`catalog` 给下游声明的 `higher_is_cleaner` 字段，在 `clipping` 和 `white_noise` 两族上**取值完全相反**。信任这个字段的 Agent 会把崩塌曲线读反。已修正。

### BUG-3：审计结果不可复现

用新写的批量确认命令去复现报告里的数字时，**干净基线完全一致，但扰动条件不一致**：

```
gaussian_snr:30   平衡准确率  0.7325  vs  0.7212   ← 差了约 9/1241 条
```

根因在 `audiomentations` 的源码里：

```python
snr   = random.uniform(self.min_snr_db, self.max_snr_db)   # Python 全局 RNG
noise = np.random.normal(0.0, self.parameters["noise_std"], ...)  # numpy 全局 RNG
```

我们**把 `min` 和 `max` 钉成相等**，以为这样就确定了。但**钉住的是目标 SNR，不是噪声波形**——噪声从两个进程级全局随机数发生器里取，而我们从未播种。

修复：在测量每个条件前**逐条件播种**（种子由条件名派生）。必须逐条件而不是每轮一次，否则音频会依赖测量顺序，分块执行就不成立了。

**这个缺陷还推翻了我们先前一个错误结论**：我们曾认为"9 次独立运行干净基线完全相同 = 全流程确定性验证通过"。那只证明了**干净基线**的确定性——它不经过任何变换。**扰动条件从来没被验证过。**

### BUG-4：`lowpass` / `highpass` 测的不是一个滤波器，而是滤波器混合体

修复 BUG-3 之后，我们拿每族一个代表性条件去比对，发现 `lowpass` 和 `highpass` 也变了。原因：

```python
# BaseButterworthFilter.randomize_parameters
random_order = random.randint(self.min_rolloff // 6, self.max_rolloff // 6)
self.parameters["rolloff"] = random_order * 6
```

滤波器**阶数**是逐条音频随机取的，而 `LowPassFilter` 默认 `min_rolloff=12, max_rolloff=24`——**我们只钉了截止频率，从没钉过阶数**。

也就是说：**"lowpass:900 Hz" 实际测的是 2 阶、3 阶、4 阶三种滤波器的平均**，一个完全没被控制的干扰参数。

这和 BUG-3 性质不同：播种让它**可复现**了，但它仍然**不是良定义的测量**。修复：把阶数钉在 18 dB/oct（库默认区间 [12,24] 的中点，刻意选择以最小化对该数的影响）。

这两个修复影响 9 族中的 4 族（`gaussian_snr`、`white_noise`、`lowpass`、`highpass`），影响幅度 0.004~0.011——**都在置信区间内，没有任何一个塌缩判定因此翻转**。所以结论不变，但数字必须重测。

> 说句实在话：**如果没做那次"证据一致性"验证，BUG-3 和 BUG-4 会一直躺在最终报告里。** 尤其 BUG-4——它意味着我们报告的 `lowpass` 阈值其实测的不是一个滤波器。评审真要较真，这是会被问住的。

## 5. 结论与可直接复用的部分

**对这个模型的结论**（仅限 `superb/wav2vec2-base-superb-er` + IEMOCAP）：

不该采信其输出的条件：
- 加性噪声 SNR 低于 ≈5 dB（塌缩到常数 happy）
- 低通截止低于 ≈850 Hz（塌缩到常数 neutral，**但准确率仍有 0.44~0.50，准确率监控抓不到**）
- MP3 码率低于 ≈16 kbps（→ neutral）
- 固定幅度噪声高于 ≈0.02（→ happy）
- 时间拉伸到 1.5× 及以上（→ neutral）

可以耐受的：MP3 ≥32 kbps、削波 ≤10%、音高 ±2 半音、高通 ≥100 Hz、SNR ≥30 dB。
**但音量变化（gain）在任何档位都有损失**——这是最容易被忽略的一条。

**可直接复用的方法学部分**（与具体模型无关）：

1. **区分"不确定"与"塌缩"**，并监控**预测多样性**而不只是准确率
2. **用 P(degenerate) 代替二元判定**——对噪声估计施加阈值，不该报成确定结论
3. **探路与确认分离**，报告只引用确认阶段——小样本会给假发现
4. **阈值必须报告括号区间和采样步长**，并注明是推断而非观测
5. **验证阈值是否依赖评测集**：换构成、换 session、换抽样种子
6. **失败的测量必须显式标记**，绝不能回退成一个看起来正常的结果
7. **随机性要逐条件播种**，否则分块/并行执行会改变结果

## 6. 局限与声明

**局限**（这些必须说清楚，否则结论会被过度解读）：

- **只测了一个模型**。这里的任何结论都不构成对 wav2vec2 或 SER 模型的普遍断言
- **只用了一个数据集**（IEMOCAP，英语、表演式语音）。不是自然口语、不是其他语种
- **塌缩判据是我们定义的约定**（`majority_share ≥ 0.75` 或 `entropy ≤ 0.30`）。换定义边界会移动；`P(degenerate)` 报告的是在**这个**定义下数据支持度有多高
- **阈值全部是括号推断**，不是观测到的精确值
- `highpass` 和 `clipping` 在测试范围内没有塌缩，**不代表它们安全**，只代表"在这个范围内没测到"

**第三方素材与来源**：

- 被测模型：`superb/wav2vec2-base-superb-er`（Apache-2.0）
- 数据集：IEMOCAP（需签署使用协议）
- 音频变换库：`audiomentations`（MIT）
